# Актуальность проекта

Зачастую сотрудники компании тратят достаточно много времени на работе на простой поиск ответов во внутренных документах компании, что бьет по продуктивности команды. 
В качестве решения проблемы в моменте можно использовать поиск по ключевым словам, но такой метод имеет сильный недостаток - простой поиск по ключевым словам не понимает контекста, из-за чего очень часто не особо поднимает продуктивность поиска по сравнению с ручным. 
Поиск по ключевым словам актуален для простых и логически, а также синтаксически четких вопросов. Когда же вопрос сложный и не может быть четко описан как простой текс например (то есть когда важен контекст/семантика) намного лучше подошло бы автоматизированное решение, которое само выполняет поиск, и, что очень важно, обращает внимание на контекст.

Именно по этому целью проекта стала разработка локального сервиса на основе RAG, отвечающего на вопросы на человекочитаемом языке по заранее представленному корпусу текстов. 

Также важно, что зачастую внутренние документы компаний подразумевают конфиденциальность, то есть то, что их нельзя, например, отправить на сторонний сервер для анализа и получения ответов на вопросы. Поэтому нужно, чтобы сервис мог разворачиваться внутри компании в ее пределах. К тому же это решает вопрос с возможными проблемами доступности стороннего сервера, например если он заблокирован. 

Для того, чтобы автоматизированное решение, направленное на поиск определенного текста во всем массиве, могло дать правильный ответ с учетом семантики, простое программное решение не подойдет. Следует использовать технологии машинного обучения, а именно языковые модели нейронных сетей, то есть LLM. Однако LLM без контекста может галлюцинировать, что негативно сказывается на работе сервиса. Поэтому следует также использовать RAG, который сочетает в себе поиск с учетом семантики и генерацию, что позволяет давать намного более точные ответы и даже отсылки к источнику этого ответа (например на конкретный блок текста их общего массива).

Таким образом будет реализована не просто классификация или регрессия в классическом понимании, а комбинированный пайплайн. 

# Метрики

Для оценки точности поиска надо использовать некоторые метрики. В нашем случае отлично поддойдут следующие:

1) Faithfulness
2) Recall (recall_fuzzy с применением стеммера)
3) time

Faethfulness это метрика, отображающая долю ответов без галлюцинаций относительно всех данный ответов. Для получения данной метрики есть смысл использовать еще одну LLM в качестве судьи, а также частично выполнять проверку "вручную".
Метрика Recall@5 отображает долю от всех запросов для случая, когда из запроса хотя бы 1 релевантный фрагмент попал в топ 5.
Метрика time показывает среднее время ответа модели и может зависеть не только от конкретной модели, но и от нагрузки на сервер обращений, типа работы (локально/сервер OpenRouter), количества топ-к в запросе, сложности запроса и системного промпта.

# Ограничения

Сервис предназначен исключительно для документов на английском и русском языках. Пока что на двух, но вдальнейшем будет рассмотрен вариант усовершенствования для работы с другими языками. 

Размер документа должен быть не более 200 страниц. Если больше, может потребоваться еще один слой дополнительной обработки. 

Локальное развертывание сервиса. Это значит, что не должно быть никаких отправок по внешним API, только внутри компании. В качестве варианта, где будет развернута LLM рассматривается Ollama. 

Поскольку для работы с чанками и локальным развертыванием LLM требуется больше производительности железа, чем у чипа от микроволновки, сервис предполагается разворачивать на сервере с GPU, либо с достаточно мощным процессором, который позволил бы работать без графического ускорителя. 

В случае же в работой по API с OPenRouter будет достаточно условного офисного ноутбука.

Проект можно считать кроссплатформенным благодаря реализации в виде докер-контейнера, что позволяет запускать его и на Windows, и на Linux, и на macOS. 

Запросы к модели/серверу должны быть сформулированы четко и относиться непосредственно к тематике загруженных документов. В ином случае модель не сомжет корректно сгенерировать ответ и выдаст сообщение об отсутствии информации в представленных материалах.

# Допущения

Документы должны быть приемлемые в плане читаемости текста в них, то есть отсканированный 30 лет назад при помощи мыльницы рукописный документ будет нечитаем для сервиса, а текстовый документ `.pdf`, экспортированный из word - отлично подойдет.

Запрос формулируется на том же языке, что и текст в искомом документе.

Сервис не заменяет эксперта полностью, а лишь ускоряет процесс поиск необходимой информации в контексте.

# Ожидаемый эффект от интеграции проекта в компанию

Время поиска информации во внутренных документах, затрачиваемое работниками компании снизится, засчет чего возрастет продуктивность. Из этого вытекает, что снизится нагрузка на экспертов, ведь теперь за повторным профильным вопросом по документам сотрудник пойдет не к эксперту, а отправит запрос в сервис по поиску. 

В случае локального развертывания также снижается шанс отрицательного роста конфиденциальности и утечек данных из-за человеческого фактора, поскольку вместо того, чтобы попробовать поискать ответ на стороне сотрудник воспользуется нашим сервисом.

# Текущий статус проекта

На настоящий момент проект полностью функционален и включает 2 рабочих варианта реализации:

1) Полностью локальное развертывание языковой модели на собственных мощностях, что обеспечивает возможность быстрого получения ответов на вопросы по внутренней документации.
2) Локальный сервис для ответа на вопросы, локально обрабатывающий тексты, после чего они отправляются модели на сервере OpenRouter. В запросе передается только вопрос пользователя, топ-к и контекст, что сохраняет конфиденциальность, но лишь частично в отличие от локальной модели.

В обоих вариантах реализована обработка текстов форматов `.txt `, `.pdf`, `.md`, а также их очистка и предобработка. Реализован гибридный поиск (dense + sparse) с переранжированием при помощи cross-encoder. Есть API на FastAPI с тремя эндпоинтами: `/ask`, `/health`, `/docs`.  

В будущем рассматривается возможность улучшения генерации ответа модели, использования других моделей и улучшение предобработки текстов.
