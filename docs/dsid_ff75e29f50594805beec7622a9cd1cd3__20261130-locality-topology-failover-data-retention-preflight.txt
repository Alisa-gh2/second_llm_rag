Samir/Team —

A few technical points to surface before the call that often impact node/storage choices:

1) Locality & failure domains
- Prefer node labels of the form: topology.kubernetes.io/zone and topology.kubernetes.io/rack. Use PodTopologySpreadConstraints to distribute replicas across rack boundaries.
- For RTO ~2h in a single rack-failure, plan for at least a cross-rack warm cache strategy: keep a % of KV cache checkpoints replicated to the other rack every 30–60 minutes (async) so warm-up time is bounded.

2) PV strategy + binding
- For model artifacts that require ReadWriteMany, if you can't run Ceph, we recommend S3-backed CSI for model pulls with a small local cache (ephemeral) to avoid cross-mount latencies.
- For checkpoint durability, use blockstore with synchronous replication across the two failure domains for critical artifacts; non-critical artifacts can use eventual replication with lifecycle policies.

3) Eviction handling for large KV caches
- Use local-ssd with a qosClass Guaranteed for cache pods if possible; configure the kubelet eviction thresholds to prefer evicting best-effort workloads over GPU-serving pods.
- Expose a cache-compact endpoint in your cache agent so Redwood's runtime can trigger compaction before large-scale eviction events.

4) Node sizing and autoscaling hints
- Recommend GPU nodes sized for 8 A100s per node (or equivalent) with a separate 2-node hot-spare pool for fast failover. Use ClusterAutoscaler with scale-down disabled for hot-spares.
